# MIMS Next — 下一代集成测试平台（初期思考）

> 状态：概念与架构酝酿阶段（非实现规格）  
> 目标：面向 ATE（Automated Test Equipment）构建**行业领先**的模块化集成测试平台  
> 基准参考：现有 MIMS / NI TestStand / LabVIEW / ATECloud 及同类通用 ATE 平台

---

## 1. 我们要解决什么问题

现有 **MIMS（Modular Integrated Measurement System，模块化集成测试系统）** 已在光通信无源/有源产品产线跑通「统一界面 + 产品测试程序 + 统一设备驱动」三层模型，并与无纸化 / MES 打通。它解决了「项目各自为政、UI 碎片化、仪器驱动重复建设」的历史痛点。

下一代平台要在此之上回答更难的问题：

| 维度 | 现状痛点（从遗产系统观察） | 下一代要达到的状态 |
| --- | --- | --- |
| 开发效率 | TP 以 DLL + 手写代码为主，调试工具链偏重 | 序列编排 / 图形化 / 代码混编，分钟级搭通标准流程 |
| 仪器抽象 | UDL 统一接口有价值，但部署/版本/注册脆弱 | 驱动即插即用、型号互换、契约化与仿真优先 |
| 部署运维 | 桌面安装、路径权限、DLL 版本冲突频发 | 边缘节点标准化 + 云端配置/发布/观测 |
| 数据资产 | 测试结果分散，分析与追溯偏弱 | 全链路可追溯、报告/洞察/SPC 原生能力 |
| 生态协作 | 工程师门槛高，跨角色协作成本大 | 操作员 / AE / 平台 / IT 分层体验一致 |
| 行业水位 | 对标桌面 ATS 时代 | 对标 TestStand 级序列引擎 + LabVIEW 级仪器生态 + ATECloud 级云化体验 |

**一句话定位（草案）：**  
> 面向**光通信既有产线**的 **工业级 ATE 操作系统**——先把 MIMS 场景做到行业领先，再向外扩展；本地实时可靠执行，云端统一编排与资产治理，开发体验达到或超越主流通用平台。

**首期战场（已拍板）：** 光通信既有产线（现有 MIMS）→ 行业领先；通用电子/射频等垂直场景列为后续扩展，架构预留扩展点但不抢首期范围。

## 2. 遗产系统速览（MIMS Today）

资料来源：`工程思考/04_架构设计与技术治理/2-MIMS` 下用户手册、概要设计、TP 调试工具说明等。

### 2.1 三层架构（核心遗产，建议继承精神）

```text
┌─────────────────────────────────────────────┐
│  UUI  Uniform User Interface                │  权限 / 过程展示 / SN 入口 / 菜单
│  + Web 配置系统 / 消息交换框架               │
├─────────────────────────────────────────────┤
│  TP   Test Program（产品业务 DLL）           │  测试项 / 算法 / 规格限 / 流程
├─────────────────────────────────────────────┤
│  UDL  Uniform Device Library                │  OSA/TLS/PM/开关/衰减/温箱…
└─────────────────────────────────────────────┘
         ↕ MES / 无纸化 / OPC / 数据管理
```

### 2.2 已验证的价值

- **统一体验**：生产 / 调试 / 研发模式分离，角色权限清晰。
- **TP 热插拔**：按 PN / SN 加载对应测试模块，降低产线培训成本。
- **仪器抽象**：同类型设备统一函数接口，支撑产线换机。
- **制造闭环**：对接无纸化工艺流、规格限、结果回传。

### 2.3 已知约束（下一代必须显式攻克）

- 技术栈绑定 Windows + .NET Framework + 本地 DLL 生态。
- UUI↔TP 以 XML/本地 Socket 通信，分布式与可观测性不足。
- 版本、路径、注册表、VISA、权限问题导致现场故障模式多（见既有排错文档）。
- TP 开发偏「程序员友好」，对工艺/测试工程师的低代码路径不足。
- 云侧能力停留在 Web 配置，尚未形成真正的「测试云平台」。

## 3. 行业对标：学什么、超什么

### 3.1 NI TestStand — 序列引擎与产线治理标杆

应吸收：

- **Sequence / Step 模型**：测试即编排，而非散落函数调用。
- **Process Model**：Batch / Parallel / Sequential 等产线模型一等公民。
- **结果处理管道**：回调、报告、数据库、失败处理策略可插拔。
- **多语言适配器**：LabVIEW / .NET / Python / C/C++ 同台协作。
- **部署与版本**：序列、依赖、配置可打包发布。

我们要超越/差异化的点：

- 更深的 **MES / 无纸化 / 光通信工艺语义**（SN-PN-工艺流-规格限原生）。
- 更现代的 **云端资产管理与远程运维**（不只是桌面序列编辑器）。
- 更强的 **边缘确定性执行**（抖动、超时、仪器会话生命周期）。

### 3.2 LabVIEW — 仪器与测量生态标杆

应吸收：

- 仪器驱动与测量原语的丰富度、可视化调试。
- 硬件抽象 + 仿真（硬件未到也能开发）。
- 工程师友好的数据流/面板思维（不必全员写 C#）。

我们要超越/差异化的点：

- 避免重度锁定单一图形语言；采用 **「可视化编排 + 专业代码扩展」** 双轨。
- 平台内核开放、可自托管，数据与 IP 留在企业内部。
- 针对产线 ATE：**防呆、权限、追溯、节拍** 优先于实验室灵活度。

### 3.3 ATECloud（纳米软件等云化零代码方向）— 体验与云化标杆

应吸收：

- **零/低代码拖拽** 搭流程，缩短从仪器到方案的路径。
- **多接口即插识别**（LAN/USB/GPIB/RS232/485）与边缘网关思路（如 ATE-BOX）。
- **报告 / 数据洞察** 作为平台能力，而非项目附赠。
- B/S 或云端协同：配置、监控、分析随时可达。

我们要超越/差异化的点：

- **工业强度**：复杂光模块/无源测试算法、长稳、多工位并行、失败恢复。
- **可扩展编程模型**：零代码覆盖 80% 标准场景，20% 复杂场景用一等公民 SDK（Python/.NET/C++）。
- **企业级治理**：多工厂、多产线、审计、权限、变更发布、灰度回滚。

### 3.4 其他通用 ATE 平台共性（行业领先清单）

行业领先平台通常同时具备以下能力层：

1. **Execution Runtime** — 确定性、可中断、可恢复、支持并行工位  
2. **Sequence / Workflow Studio** — 可视化 + 代码混编  
3. **Instrument Abstraction** — 驱动商店、仿真、互换矩阵  
4. **Data Plane** — 原始波形/曲线 + 结构化结果 + 血缘  
5. **Ops Plane** — 配置中心、发布、远程诊断、指标看板  
6. **Integration Fabric** — MES/ERP/PLM/SPC/OPC-UA  
7. **Security & Compliance** — 角色、审计、电子签名、变更管控  

MIMS Next 的「行业领先」定义，建议用这 7 层做雷达图自评与路线图打分。

## 4. 目标愿景：MIMS Next 能力北极星

### 4.1 产品原则

1. **可靠优先于炫技**：产线宕机成本高于功能数量。  
2. **分层体验**：操作员极简；AE 编排高效；平台工程师可深挖。  
3. **契约优于约定**：TP / Driver / UI / MES 全部接口版本化。  
4. **仿真即默认**：无硬件可开发、可 CI。  
5. **云边协同**：边侧执行实时与隔离；云侧编排、资产、洞察。  
6. **开放可替换**：核心开源协议或清晰插件 ABI，避免第二代锁定。

### 4.2 目标用户与场景

| 角色 | 核心场景 |
| --- | --- |
| 产线操作员 | 扫 SN、一键测、清晰 Pass/Fail、防呆 |
| 测试/工艺 AE | 搭序列、调规格、分析不良、快速改版 |
| 仪器/驱动工程师 | 接入新设备、互换验证、仿真模型 |
| 平台/软件工程师 | Runtime、插件、性能、集成 |
| 质量 / IT / 制造系统 | 追溯、SPC、MES、权限审计 |

### 4.3 成功度量（草案 KPI）

- 新标准产品测试方案搭建时间：从「周」降到「天/小时」  
- 新仪器接入：契约驱动，目标 ≤ 1 人日完成基础控制面  
- 现场因版本/依赖导致的启动失败率显著下降  
- TP 复用率、跨产线配置一致性提升  
- 测试数据从产生到可分析的时延进入近实时  
- 关键与回滚可审计、可灰度

## 5. 架构草案（讨论用，非定稿）

```text
                         ┌──────────────── Cloud / Factory Hub ────────────────┐
                         │  Asset Registry · Config · Release · Observability  │
                         │  Data Lake/Warehouse · Report · SPC · Insight UI    │
                         │  Identity · Policy · Audit · MES Connector Hub      │
                         └───────────────────────┬─────────────────────────────┘
                                                 │ secure sync / MQTT / gRPC / HTTPS
┌──────────────────────── Edge Station (ATE Node) ────────────────────────────┐
│  Operator Console (Web/Desktop shell)                                        │
│  Sequence Runtime  ← Process Models / Parallel Stations                      │
│  TP Pack Runtime   ← sandboxed modules (compat shim for legacy TP optional)  │
│  Instrument Bus    ← Driver plugins + VISA/SCPI/custom + Simulator           │
│  Local Cache / Store-and-Forward · Device Health · Watchdog                  │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 5.1 建议的逻辑子系统

| 子系统 | 职责 | 对标灵感 |
| --- | --- | --- |
| **Studio** | 序列/面板/规格/报告模板编辑 | TestStand + ATECloud 体验 |
| **Runtime** | 执行引擎、节拍、并行、恢复 | TestStand Process Model |
| **Driver Hub** | 仪器能力模型、发现、仿真 | LabVIEW/IVI + UDL 进化 |
| **TP Pack** | 产品测试包（算法+序列+资源） | 现有 TP DLL 的下一代形态 |
| **Data Plane** | 结果、曲线、附件、血缘 | ATECloud 报告/洞察 |
| **Control Plane** | 配置、发布、权限、审计 | 现有 Web 配置系统进化 |
| **Integration** | MES/无纸化/OPC/企业系统 | 现有 Paperless 接口现代化 |

### 5.2 与现有 MIMS 的演进策略（三种备选）

**A. 兼容演进（推荐作为起步）**  
保留 UUI/TP/UDL 语义，先做 Runtime + Driver Hub + Control Plane 现代化，提供 Legacy TP Adapter，产线可渐进迁移。

**B. 双轨并行**  
新平台独立建设，关键产线试点；旧 MIMS 维护至 EOL。风险隔离好，短期成本高。

**C. 云原生重写**  
全面 B/S + 容器化边缘。体验最干净，但对现有 DLL/算法资产冲击最大，需极强迁移工具。

> 初期建议：**A 为主、B 试点**——先拿到「可运行的现代化 Runtime + 云控」，再逐步收回 Studio 体验差距。

## 7. 分阶段路线（初期规划）

### Phase 0 — 对齐与基线（当前）

- 澄清业务边界、成功标准、必须兼容的产线清单  
- 完成对标差距雷达图与风险清单  
- 固化本 README 中的原则与非目标

### Phase 1 — 骨架验证

- Runtime MVP：顺序执行、步骤结果、中断/恢复  
- Driver Hub MVP：2–3 类真实仪器 + 全仿真  
- Legacy TP Adapter 可行性验证  
- 基础可观测：日志、步骤时序、设备会话

### Phase 2 — 产线可用

- Operator Console + 权限/模式  
- MES/无纸化关键路径打通  
- 配置发布与版本回滚  
- 报告与基础 SPC

### Phase 3 — 行业领先体验

- Studio 低代码编排成熟  
- 多工位并行 / 复杂 Process Model  
- 数据洞察与企业集成生态  
- 驱动商店与第三方扩展生态

## 8. 非目标（初期刻意不做）

- 不追求第一天替换全部现有 TP。  
- 不做「又一个纯 LabVIEW 克隆」。  
- 不把所有算法搬进云端实时执行（边侧确定性优先）。  
- 不在未验证产线可靠性前铺开全工厂切换。
