# 00.1 为什么要对 MES 业务建模

> 所属篇章：00_MES业务建模总纲 ｜ 状态：✅ 已完成

## 本篇要回答的业务问题

- 为什么「功能清单驱动」的 MES 项目容易失败，而建模驱动能降低风险？
- 业务建模在 MES 项目中具体解决什么问题？
- 建模的产出物有哪些，分别回答什么问题？

## 1. 没有建模的 MES 会遇到什么

MES 调研（见 [`MES调研.md`](../../MES调研.md)）中有一个核心论断：**直接做「大而全 MES」失败概率极高**。这不是实施能力问题，而是方法论问题——功能清单堆得越长，系统越难说清自己的边界。没有统一业务模型的支撑，典型失败模式有以下五类：

| 失败模式 | 现场表现 | 根因 |
| --- | --- | --- |
| 需求蔓延 | 功能越堆越多，无人说得清系统边界 | 没有对象地图，「加功能」变成唯一演进方式 |
| 术语混乱 | 工单 / 批次 / Lot / SN，各系统、各部门各说各话 | 缺少统一语言（Ubiquitous Language） |
| 状态不一致 | 同一个 SN 在不同模块的状态互相打架 | 状态机没有被显式定义，各模块各自维护状态字段 |
| 追溯断链 | 出了质量问题，回答不了「当时到底发生了什么」 | 只存了「当前状态」，没存「事实事件」 |
| 规则隐式化 | 工序顺序约束、放行规则散落在代码和人脑中 | 规则没有可视化模型，无法评审、无法演进 |

这五类问题有一个共同点：**它们都是「模型缺失」问题，不是「功能缺失」问题**。加再多功能页面，也补不回一张缺失的状态机定义。

一个直观的对照：

```mermaid
flowchart TB
    subgraph 功能驱动[功能清单驱动]
        F1[收集功能清单] --> F2[逐个开发页面]
        F2 --> F3[术语 / 状态各自定义]
        F3 --> F4[集成时发现互相矛盾]
        F4 --> F5[返工修数据结构]
    end
    subgraph 建模驱动[业务建模驱动]
        M1[统一语言与对象地图] --> M2[状态机与事件显式化]
        M2 --> M3[功能只是模型的投影]
        M3 --> M4[模型稳定，功能增量叠加]
    end
```

功能是「模型之上的投影」：页面、接口、报表都只是对同一组业务对象的不同视图。模型稳了，功能才能便宜地加；模型乱了，每个新功能都在制造新的不一致。

## 2. 业务建模的价值

- **统一语言（Ubiquitous Language）**：业务、工艺、IT 用同一套词汇讨论同一个东西。当「过站」「工单」「测试批次」在会议、代码、接口契约中指向同一个精确定义时，沟通成本和误解率同时下降。本仓库的术语基准是 `AGENTS.md` 核心领域概念表（WorkOrder、Station、TestFlow、RouteStep、SerialUnit、TestRecord、TraceEvent）。
- **边界划分**：明确 MES 管「执行」不管「计划」，划清与 ERP / APS / WMS 的边界。ISA-95 的 L3/L4 分层（见 [`ISA-95学习指南.md`](../../架构和系统设计/ISA-95学习指南.md)）提供了判断标尺：排产、仓储、企业级成本核算不属于 L3；而单件执行、过站门控、事实记录、追溯是 L3 的本职。
- **显式化**：把状态机、校验规则从代码与人脑提升为可视化模型，便于评审与演进。例如「失败品未处置不得过站」这条规则，在模型中以 `MES-4002` 错误码与状态迁移约束的形式可见，工艺与质量人员无需读代码即可参与评审。
- **演进基础**：模型稳定则功能可增量叠加（对应本仓库 M1 → M2 → M3 里程碑策略）。M1 落地执行闭环时建立的 SN 状态机，在 M2 收紧为强门控、M3 上叠加追溯看板，全程不需要推翻重建。

| 价值 | 检验方式 |
| --- | --- |
| 统一语言 | 新成员能否在一天内用文档术语与工艺正确对话 |
| 边界划分 | 面对任何新需求，能否快速回答「这是 MES 的事吗」 |
| 显式化 | 规则变更时，评审对象是图而不是代码 diff |
| 演进基础 | 里程碑切换时，核心实体是否保持稳定 |

## 3. 建模产出物

| 产出物 | 回答的问题 | 本目录位置 |
| --- | --- | --- |
| 类图（Class Diagram） | 有哪些业务对象、彼此什么关系 | 01.3 / 08.1 |
| 状态机（State Machine） | 对象生命周期与合法流转 | 04.2 / 04.3 / 05.4 |
| 时序图（Sequence） | 一次业务动作的参与者协作 | 04.4 |
| 活动图（Activity） | 端到端流程与异常分支 | 02.3 / 08.2 |
| 事件模型（Event） | 事实如何被记录 | 05.1 |

产出物之间的关系是互补而非重复：**类图给静态骨架，状态机给生命周期，时序图给协作细节，活动图给流程全貌，事件模型给事实底座**。同一业务用五种视图反复检验，才能保证「不重不漏」。

## 4. 与本仓库实现的关系

建模不是文档装饰，它直接决定了 `design.md` 的结构：

| 建模对象 | 实现落点 |
| --- | --- |
| 对象地图（00.4） | `design.md` §4.1 核心实体（WorkOrder、Station、SerialUnit、RouteStep、TestRecord、TraceEvent） |
| 状态机（04.2 / 04.3 / 05.4） | `design.md` §4.2 关键状态机（`SerialStatus`：Created → InProcess → TestedPass / TestedFail → Rework / Scrapped → Done） |
| 六问模型（00.2） | API 契约 `design.md` §8 的分组逻辑（工单/流程 → 测试/追溯） |
| 业务原则 | `design.md` §1（先记录、再约束、后分析；先小后大；设备不稳定假设） |

反向也成立：实现是建模的检验。当代码里的 `SerialUnit.PendingStepSequence` 无法回答模型里「下一站必须是下一个未完成步骤」这条不变量时，说明模型或实现有一方需要修正。建模与实现的对照入口见 [README.md](../README.md)「与代码实现的对照入口」表。
