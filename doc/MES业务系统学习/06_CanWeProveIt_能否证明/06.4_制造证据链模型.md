# 06.4 制造证据链模型

> 所属篇章：06_CanWeProveIt 能否证明 ｜ 状态：✅ 已完成

## 本篇要回答的业务问题

- 记录了就等于能证明吗？从「有数据」到「可举证」差什么？
- 证据链的要素是什么：事件 → 记录 → 签名 → 时间 → 不可篡改？
- 数据完整性原则（ALCOA）如何在模型中落地？

## 1. 从记录到证据

**记录（Record）与证据（Evidence）的区别**：记录是「存了」；证据是「在质疑下站得住」——客诉、审核、法庭场景中，数据会被追问来源、时间、责任人、是否被改过。**记录是技术产物，证据是信任产物**：

| 层次 | 说明 | 模型支撑 |
| --- | --- | --- |
| 事实 | 发生了什么 | ManufacturingEvent（05.1） |
| 记录 | 事实被固化，附时间与上下文 | TraceEvent / TestRecord |
| 签名 | 责任被归属到人 | 电子签名 / 审批（03.2 / 05.4） |
| 完整性 | 事后无法无痕篡改 | 审计日志 + 追加式设计 |

四层逐级加强：有事实无记录 = 没发生（系统视角）；有记录无签名 = 不知道谁负责；有签名但可随意改 = 责任可伪造。**证据链 = 四层同时成立的闭环**。

## 2. ALCOA 原则映射

ALCOA 是制药/器械等受监管行业的数据完整性（Data Integrity）标尺（GxP 语境），MES 借用它做自查清单——满足 ALCOA 不需要额外功能，靠的是前几篇的模型设计：

| 原则 | 中文 | 模型落点 |
| --- | --- | --- |
| Attributable | 可归因 | 事件携带操作员（5M1E - Man）——`TraceEvent.OperatorId`；鉴权后由上下文注入，不可前端伪造 |
| Legible | 清晰可读 | 结构化记录 + 原始报文保留——`Metrics` 可查询，`RawPayload` 可复核 |
| Contemporaneous | 同步记录 | EventTime（发生时间）与记录时间分离——补传场景双时间还原现场顺序 |
| Original | 原始 | RawPayload 原始报文——仪器第一手输出，含解析前信息 |
| Accurate | 准确 | 判定规则版本化（05.2）——每条判定可解释为「依据哪版规格」 |

进阶为 ALCOA+（+Complete 完整、+Consistent 一致、+Enduring 持久、+Available 可用）时的模型对应：

| +原则 | 落点 |
| --- | --- |
| Complete 完整 | 5M1E 上下文按风险采集（03.4 取舍） |
| Consistent 一致 | 状态 = 事件重放（04.2 §2）；指标字典统一（01.3 INV-6） |
| Enduring 持久 | 归档与保留期限（00.3 EOL 阶段） |
| Available 可用 | 追溯查询 P95 ≤ 2s（06.1 §3） |

## 3. 审计与防篡改

- **审计范围**：工单状态变更、手动放行、规则变更（对照 `design.md` §9.3）——共同特征是「人工干预了系统自动判定」，是质疑时最先被检查的动作。
- **追加式设计：事件不可修改，纠正 = 新事件（不覆盖旧记录）**——这是防篡改的第一道且最重要的一道防线：不是「防住改数据的权限」，而是**让改数据这个动作本身无法表达**（只有追加通道）。纠错流程：发现 TestRecord 数值错误 → 不 UPDATE 原记录 → 写 CorrectionEvent（引用原记录 + 正确值 + 原因 + 审批人）→ 查询层合并展示。
- 审计日志与业务事件的职责分工：业务事件（TraceEvent / TestRecord）记录制造事实；审计日志（AuditLog）记录**人对系统的干预**（谁改了规则、谁放行了）。两者通过明确标识关联（如 DisposalEvent 关联 AuditLog Id）。
- **哈希链 / 归档（长期演进方向，可选）**：对高合规场景（客户要求强证明），可对事件流做逐条哈希链（每条事件含前条哈希）或周期性锚定（Merkle 根存外部），使「任何历史篡改都可被数学检测」。第一阶段不做——追加式设计 + 权限控制已满足常规审计；哈希链是客户合同要求出现时的增强项。

## 4. 证据链可视化

追溯视图如何呈现证据链——**给审核者的不是数据表，而是可朗读的叙事**：

| 呈现层 | 内容 | 设计要点 |
| --- | --- | --- |
| 时间线 | 事件按 OccurredAt 排列，标注事件类型图标 | 处置、审批事件显式突出（不与普通过站混排） |
| 责任人 | 每事件显示 OperatorId / 审批人 | 审批显示「理由」摘录 |
| 版本 | 关键节点显示当时生效的流程 / 规格版本 | 防「以今论古」质疑 |
| 原始数据 | 测试记录可下钻 RawPayload | 复核入口一键可达 |
| 完整性标记 | 数据断链处显式标注（如「此站无环境数据」） | **诚实展示缺口比隐藏更可信** |

验收口径：一个从未到过产线的审核者，仅凭追溯视图就能复述「这件产品怎么造出来的、谁对每个关键决策负责」——这就是 [07.1 第 6 章](../07_综合案例/07.1_一个产品的一生.md) 客诉场景的底层能力。
